# ADR-0009: Worker, delegated execution and fencing

- **Status:** Accepted
- **Date:** 2026-11-01

## Context

Admitted tasks must run outside the API process, under an identity of their own, and only while the person who asked for them may still have them run. Workers crash, stall and are restarted, so the design must keep a task from being finished twice, keep a stalled worker from writing after another has taken over, and recover abandoned work without losing its history. Phase 1 handlers do nothing external (`noop` and `wait`); Phase 2 adds `generate`, which reaches only the configured local model (ADR-0015). No untrusted code runs, and OpenShell enforcement (Phase 3) is not claimed.

## Decisions

| Area | Decision | Rationale |
|---|---|---|
| Jobs | `aegis.jobs` (migration 0006) holds one row per attempt series: `pending`, `running` or `finished`, with `attempt`, `max_attempts`, `run_after`, the lease (`lease_owner`, `lease_expires_at`, `heartbeat_at`), `last_error_code` and the submission's request ID as `correlation_id`. A task has at most one pending or running job (partial unique index). The API creates the job in the same transaction that queues the task, and finishes it when a queued task is cancelled. A task that needs approval gets no job until it is approved (Phase 6). | The Phase 1 plan, §3.2 and §3.4: submission, job and audit commit together. |
| Rule D8 | Triggers on `jobs`: a job starts pending at attempt 0; the attempt rises by exactly 1, and only when a pending job is claimed; an expired lease cannot be renewed; a running job needs an unexpired lease; fixed columns and finished jobs never change; rows are never deleted. A worker's history row must name a running job of the same task at its current attempt, and moving a task from `queued` or `running` to anything but `interrupted` or `cancelled` needs an unexpired lease. History and decisions reference `(job_id, task_id)` by composite foreign key. `aegis_app` may insert only the job's identity, task, limit, schedule and correlation, and update only state, attempt, schedule, lease and error. | A stale worker cannot heartbeat, complete or write history, even through direct SQL as `aegis_app`. |
| Fencing | The pair (job ID, attempt) is the fencing token. Leases end at the database's `now()` plus the lease duration, so worker clocks do not matter. Every worker write locks the task, then the job with the condition `attempt = token AND state = 'running' AND lease_expires_at > now()`. If nothing matches, the worker stops the handler, discards its result, writes nothing more, logs `fence lost` and records `job.fence_lost` in its own transaction when the database is reachable. | The Phase 1 plan, §4.7. |
| Lock order | Every writer locks a task before its job (`FOR NO KEY UPDATE`). Claim and recovery find their task with `SKIP LOCKED` on the task row. Heartbeats lock only the job. | Racing workers each take a different task, and the API, worker and recovery cannot deadlock. |
| Claim | One transaction claims the job (attempt + 1, lease), makes and saves the `task.execute` decision with the job and attempt, and applies it: allow moves the task to `running`; approval required moves it to `awaiting_approval` and finishes the job; deny moves it to `failed` with the first reason as `failure_code` and finishes the job. If a cancellation was already requested (E5), the task goes on from `running` to `cancelled` and the handler never starts. | E1–E6 (ADR-0007) are checked at every claim, and nothing runs that the decision does not allow. |
| Delegated execution | The worker acts only as `system:worker`, which holds no credentials. Decisions and history name `system:worker` as the actor and the initiator as the subject. The worker process loads only the `aegis_app` password, then removes every secret variable from its own environment before any handler runs, so neither code that reads the environment nor a child process sees them. Code in the same process can still read them from `/proc/self/environ`, which keeps the initial environment, so this is not a barrier against hostile code; Phase 1 runs none, and isolating untrusted code is OpenShell's role (Phase 3). | The worker never uses the initiator's identity or credentials. |
| Running | The handler runs in its own thread with a `HandlerContext` offering only `stop_requested()`, `wait(seconds)`, `generate(request)` (Phase 2, ADR-0015) and `check_enforcement()` (Phase 3, ADR-0019, granted only to `enforcement_check` tasks). The main thread renews the lease every heartbeat interval and re-checks the fence, the cancellation flag and E2 (the initiator is still active). A cancellation request ends the task `cancelled`; a disabled initiator ends it `failed` (`initiator_disabled`). If heartbeats cannot reach the database until the lease would have ended, the worker treats the fence as lost. | The Phase 1 plan, §4.7: H4 and H6, and the checks repeated at heartbeat. |
| Outcomes | A result must be a JSON object of at most 8 KiB, measured as UTF-8, with no NaN, infinities or NUL characters; the task then ends `succeeded`. `RetryableError` interrupts the task and retries it. `HandlerFailure(code)` ends it `failed` with that code (ADR-0015). Any other error ends it `failed` (`handler_error`), and an unacceptable result ends it `failed` (`invalid_result`). | Clients cannot trigger retries, and only failures a handler marks as transient are repeated. |
| Recovery and retries | Each loop, a worker first sweeps orphaned sandboxes (at its first step, then once a minute; ADR-0019), then recovers up to 10 jobs whose lease has expired, by the database clock: the task moves `running` to `interrupted` (`lease_expired`), then to `queued` with the job pending after an exponential backoff (2 s doubling to 60 s), or to `failed` (`attempts_exhausted`). A task whose cancellation was requested is cancelled instead. Retryable handler errors take the same path. Delivery is at least once. | The expired attempt can never write again: the next claim raises the attempt. |
| Attempts | Policy `2026.11.01-2` adds `MAX_JOB_ATTEMPTS = 10`; jobs are created with that limit, and the database refuses more. `AEGIS_WORKER_MAX_ATTEMPTS` (1–10, default 3) can only lower it, and the worker refuses to start above the policy's cap. A graceful release also uses an attempt. | Configuration may only tighten a security limit (Phase 1 plan, §2.3). |
| Shutdown | On SIGTERM or SIGINT the worker stops claiming and gives a running handler `AEGIS_WORKER_SHUTDOWN_GRACE_SECONDS` to finish. If it has not, the worker halts it and releases the job with a fenced write: `running` to `interrupted` (`worker_shutdown`) to `queued`, with no backoff. | No work is lost or left leased by a planned stop. |
| Structure | `aegis.jobs.worker` runs the loop, recovery and admission; `aegis.jobs.supervision` runs the handler thread and the heartbeats; `aegis.jobs.settlement` applies every transition the worker makes, with its audit records, fenced by the lease (split in Phase 3, with no change in behaviour). | Scheduling, supervision and record keeping change for different reasons. |
| Configuration | `AEGIS_WORKER_POLL_SECONDS` (1–60, default 1), `AEGIS_WORKER_LEASE_SECONDS` (10–600, default 30), `AEGIS_WORKER_HEARTBEAT_SECONDS` (default 5, at most a third of the lease), `AEGIS_WORKER_SHUTDOWN_GRACE_SECONDS` (0–300, default 10) and `AEGIS_WORKER_MAX_ATTEMPTS`. Invalid values stop the worker at startup, as does a schema that is not current. | Operational settings, range-checked; none of them changes a decision. |
| Handlers | A closed, read-only registry with exactly `noop` (input `{}`), `wait` (`{"seconds": n}`, 0–300, stopping early when halted) `generate` (Phase 2, ADR-0015, which revises H1, H2, H5 and H6) and `enforcement_check` (Phase 3, ADR-0019, which revises H1, H5 and H6). Handlers have no outside effects, get no database, settings or credentials, return the same result for the same input, and are safe to run beside a stale copy of themselves (H1–H6). Each re-checks its input. | B5 in the Phase 1 plan: nothing beyond these kinds can run. |

## Consequences and limitations

- Delivery is at least once. A handler may run again after a crash or a lost lease; future handlers with outside effects need their own idempotency (Phase 4).
- Role changes and credential revocations during a run are not re-checked; only cancellation and E2 are, at each heartbeat. That is acceptable only because Phase 1 handlers have no side effects and run for at most 300 seconds.
- Leases compare the database's transaction start times. A write whose transaction began just before its lease expired can still commit.
- A handler that ignores its halt request keeps running in its thread until it returns; its result is discarded. Phase 1 handlers always stop.
- Lowering `AEGIS_WORKER_MAX_ATTEMPTS` applies from a task's next failure; a pending job may still be claimed once more.
- A worker exits on an unexpected error in claim or recovery rather than retrying it, so a supervisor must restart it. Containers and supervision are deferred.
- Queued tasks created before migration 0006 have no job and never run.
- Workers are processes on the same host as the database. Only `enforcement_check` uses an OpenShell sandbox (ADR-0019); every other handler runs in the worker process.

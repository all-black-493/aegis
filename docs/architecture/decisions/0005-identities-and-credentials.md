# ADR-0005: Identities, credentials and CLI administration

- **Status:** Accepted
- **Date:** 2026-11-01

## Context

The API (Increment 6) authenticates callers with bearer tokens, and the worker (Increment 10) needs an identity of its own. Authorization (ADR-0006) needs role assignments to evaluate. Before any API exists, operators need a way to create identities and tokens, and that path must not be weaker than the API that will use them.

## Decisions

| Area | Decision | Rationale |
|---|---|---|
| Identities | `aegis.identities` stores `human`, `service` and `system` identities. Names are 1–63 characters of `a-z0-9._:-` and start with a letter or digit. Only system identities, and all of them, have names beginning `system:`. An identity is never deleted and never renamed; only its status (`active` or `disabled`) can change. Triggers enforce this, including for `TRUNCATE`. | A stable identity is what audit events and future tasks point to. |
| System identities | The migration seeds `system:worker` (role `worker`) and `system:cli` (the actor recorded for CLI administration) with fixed IDs. The CLI cannot create, change or issue credentials to system identities. | The execution identity is defined by reviewed code, not by an operator. |
| Roles | `aegis.identity_roles` stores assignments. The role set is the code catalog (ADR-0006), mirrored by a `CHECK`. A trigger allows `worker` only on system identities, and only `worker` on system identities. Revoking a role deletes the row; the audit trail keeps the history. | The same rule as `ActorContext`, now enforced by the database too. |
| Token format | `aegis_pat_<lookup>_<secret>`: a 128-bit lookup ID (26 lowercase base32 characters) and a 256-bit secret (52 characters), both from `secrets`. | The lookup ID finds the row without comparing hashes. The prefix lets the log redactor and secret scanners recognize tokens. |
| Token storage | Only the lookup ID and `HMAC-SHA256(pepper, lookup:secret)` are stored, with `hash_scheme = 'hmac-sha256-v1'`. Verification uses a constant-time comparison. | The secret is random and long, so a slow password hash adds nothing. The pepper means a database copy alone cannot verify guesses. |
| Pepper | `AEGIS_TOKEN_PEPPER`: required, at least 32 characters, generated by `make setup` and `make env-upgrade`. It is loaded only by the commands that need it (`aegis credential issue` now, the API in Increment 6). | Keeps the key out of the database and out of processes that don't need it. |
| Lifetime | 30 days by default, 90 at most. No token without an expiry. Enforced in code (`aegis.identity.tokens.lifetime`) and by `CHECK (expires_at > created_at AND expires_at <= created_at + interval '90 days')`. A trigger stamps `created_at` with the transaction time, so it can't be back- or future-dated, and the CLI computes `expires_at` in the database. | Two independent checks, and the database check cannot be bypassed by supplying timestamps. |
| Credential changes | A credential is never deleted. The only change allowed is revocation, which is permanent. | Credentials stay attributable after revocation. |
| Authentication | `authenticate(connection, token, pepper)` checks, in order: missing, malformed, unknown lookup ID (after hashing anyway), wrong secret, revoked, expired, identity disabled. It returns an `ActorContext` with the identity's roles and the credential ID. Failures raise `AuthenticationError` with a reason code and, when the credential is known, the credential and identity IDs. The steps are also available separately: `presented_token()` checks the format without a database, and `verify()` does the rest. | The API can audit failures for known credentials (Increment 6) while returning one identical 401 for every reason. |
| Privileges | `aegis_app` has `SELECT` on the three tables, which authentication needs, and no write privilege. Administration runs as `aegis_owner`. | The API process cannot create identities, grant roles or issue tokens. |
| CLI | `aegis identity create\|disable\|enable`, `aegis credential issue\|revoke\|list` and `aegis role grant\|revoke`. Each command runs in one transaction as `aegis_owner`, refuses to run unless the schema is at the latest revision, and writes its audit events in that transaction with actor `system:cli` and source `cli`. `credential issue` prints the token once, alone on stdout, and its details on stderr. | The change and its audit events commit together (ADR-0010, G1). |
| Last admin | Disabling the last active admin, or revoking its `admin` role, is refused. Administration commands take a transaction-level advisory lock, so two concurrent commands cannot each remove one of the last two admins. | The API must never be left without an administrator. |
| Audit | Events: `identity.created`, `identity.disabled`, `identity.enabled`, `role.granted`, `role.revoked`, `credential.issued`, `credential.revoked` and, new in this increment, `credential.listed`. `audit_events.actor_id` now references `identities`. | Every administrative command, including listing, leaves a record. |

## Enforcement

| Rule | In code | In the database |
|---|---|---|
| Lifetime 1–90 days | `lifetime()` | `ck_credentials_lifetime` with the `created_at` stamp |
| No credentials for system identities | `IdentityAdministration` | Trigger `credentials_before_insert` |
| `worker` only for system identities | `IdentityAdministration`, `ActorContext` | Trigger `identity_roles_check_kind` |
| Identity name and kind | `IdentityAdministration` | `ck_identities_name` |
| No deletion; no change except status or revocation | — | Triggers on `identities` and `credentials` |
| `aegis_app` cannot write identity tables | — | Privileges |
| Last active admin | `IdentityAdministration` | Not enforced |
| System identities unchanged | `IdentityAdministration` | Partly: name and kind are fixed, roles are limited to `worker` and credentials are refused, but status is not protected |

## Consequences and limitations

- The CLI records `system:cli` as the actor. It cannot tell which person ran it: anyone holding the `aegis_owner` password is trusted completely, as ADR-0010 (N3) already states.
- Rules marked "in code" above can be bypassed by direct SQL as `aegis_owner`.
- Disabling an identity does not revoke its credentials. Authentication rejects them while the identity is disabled; enabling it again restores the ones that have neither expired nor been revoked.
- Changing the pepper invalidates every token. There is no pepper rotation or versioning beyond `hash_scheme`.
- `aegis_app` can read token hashes. Without the pepper they cannot be checked offline.
- Unknown lookup IDs cost the same hashing work as known ones, but the database lookup is not constant-time. Lookup IDs are not secret; the 256-bit secret is what protects a token.
- Expiry is compared with the transaction start time.
- The API accepts tokens from Increment 6 (ADR-0004).

# ADR-0010: Audit store

- **Status:** Accepted
- **Date:** 2026-11-01

## Context

Security-relevant actions must leave durable audit records (AGENTS.md §5.5). They must be kept separate from LLM observability, which may never be treated as the audit record. Phase 1 needs an audit store before any component that changes security-relevant state exists. Its guarantees must be stated exactly, without claiming more than PostgreSQL can deliver against privileged users.

The approved Phase 1 plan defines the guarantees below. They are reproduced verbatim.

## Guarantees

**Guaranteed:**
- **G1. Recorded together.** Each AEGIS service operation writes its change, its decision and its audit events in one transaction. If any write fails, none is kept and the caller gets 503. So a change made through an *uncompromised* AEGIS code path is never committed without its audit events.
- **G2. No changes by the application role.** `aegis_app` has no UPDATE, DELETE or TRUNCATE privilege on the audit table, and triggers reject those for any role that hasn't disabled them.
- **G3. Database time and correlation IDs** are on every event.
- **G4. Task history is complete.** By rules D2, D6 and D8, a task's state can't change without a history row, even through direct SQL as `aegis_app`. This covers the history table, not `audit_events`.

**Not guaranteed:**
- **N1. Authenticity.** `aegis_app` can insert made-up events, including events for changes that never happened.
- **N2. Completeness under direct SQL.** `aegis_app` can change the columns it's allowed to update without writing `audit_events`. G4 still captures task state changes.
- **N3. Owner and superuser access.** Either can disable triggers and rewrite or delete anything, undetectably.
- **N4. Tamper-evidence.** There's no hash chain, signature or external anchor, and gaps in the ID sequence (which rollbacks cause) prove nothing.
- **N5. Separately written events.** Authentication failures and denials are written in their own transactions. If that write fails, the request is still denied and a high-severity log line is written instead.
- **N6. Ordinary reads** are not audited.

**Trust boundary:** audit records can be trusted only while the API and worker processes, the `aegis_app` credentials and the owner or superuser credentials are uncompromised. Phase 1 protects the audit trail from accidental change and from a buggy application, not from a compromised application or database administrator. **The hash chain, external anchoring, separating who may write audit records, and verification tools are deferred to Phase 5.**

## Decisions

| Area | Decision |
|---|---|
| Table | `aegis.audit_events`. The primary key `event_id` is a UUID generated by the application. `id` is a database-generated, unique sequence used for ordering. |
| Fields | `occurred_at`; `event_type`; `source` (api, worker, cli, system); `outcome` (success, failure, denied); `actor_id` and `actor_kind` together; `target_type` and `target_id` together; `task_id`; `job_id`; `decision_id`; `request_id`; `reason_code`; `policy_version`; `details`. `actor_id` references `identities` (Increment 5). `task_id` and `decision_id` reference `tasks` and `security_decisions` (Increment 7); the foreign key to jobs is added with that table. |
| Database constraints | `CHECK` constraints on every format and value set. `details` must be a JSON object of at most 4 KiB. |
| Privileges | `aegis_app` has column-level `INSERT` only: no `SELECT`, `UPDATE`, `DELETE` or `TRUNCATE`, and it cannot supply `id` or `occurred_at`. The owner reads the table; no API reads audit records in Phase 1. |
| Triggers | `audit_events_stamp` sets `occurred_at` to the transaction time. `audit_events_no_update_delete` and `audit_events_no_truncate` reject changes from any role, including the owner. The trigger functions pin `search_path` and are not executable by `PUBLIC`. |
| Events | The code catalog (`aegis.audit.events`) lists each event type and its allowed detail keys. Values must be strings of at most 256 characters, integers, booleans or null. Errors name keys, never values. The database checks only the event type's format, so new types need a reviewed code change, not a migration. |
| Redaction | `AuditRecorder` passes `target_id` and every string detail through the same redactor as the logs: registered secrets plus credential patterns. |
| Inserts | Core `INSERT` without `RETURNING`, because `aegis_app` cannot read the table. |

## Consequences and limitations

- Every limitation in N1–N6 applies.
- `occurred_at` is the transaction start time, so events in one transaction share a timestamp. `id` gives their order.
- The audit table grows without limit in Phase 1. Retention and archiving are out of scope.
- Making `event_id` the primary key avoids fetching a sequence value that `aegis_app` is not allowed to read.

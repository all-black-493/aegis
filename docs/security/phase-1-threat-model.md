# Phase 1 threat model

- **Status:** Accepted for Phase 1
- **Date:** 2026-11-01
- **Covers:** the code as built at the end of Phase 1. Later phases revise this document.
- **Phase 2:** the [Phase 2 threat model](phase-2-threat-model.md) covers the `generate` task kind and the model boundary. Everything here still holds unless it says otherwise.

## 1. Scope

**In scope.** These run on one host and share one PostgreSQL 17 database:

- the HTTP API (`make api`, bound to `127.0.0.1`);
- the worker (`make worker`, any number of processes);
- the administration CLI (`aegis`);
- the database roles `aegis_app` (API and worker), `aegis_owner` (migrations and administration) and the bootstrap superuser.

**What actually runs.** Tasks are of two built-in kinds:

- `noop`, which returns at once;
- `wait`, which sleeps for 0 to 300 seconds.

Neither has any effect outside AEGIS.

**Out of scope, because it is not built:**

- **Agents, models and runtime enforcement:**
  - agents, models and prompts (Phases 2 and 4);
  - NVIDIA OpenShell and every form of runtime isolation (Phase 3);
  - provenance (Phase 5), approvals (Phase 6) and evidence verification (Phase 7).
- **Packaging:** containers for the API and worker are planned but not built. Today both run as processes on the developer's host.
- **What follows:** AEGIS does not claim filesystem, network or process isolation. **No untrusted code runs in Phase 1.**

## 2. Assets

| Asset | Where it lives | Why it matters |
|---|---|---|
| API tokens | Held by clients; stored only as a peppered HMAC-SHA256 (`credentials.secret_hash`) | A token lets its holder act as the identity |
| Token pepper | `.env` (mode 600), loaded by the API and CLI | Needed to verify or forge any token hash |
| Database passwords | `.env` (mode 600), one per role | `aegis_app` can write decisions, history and audit; `aegis_owner` and the superuser can change anything |
| Identities, roles and credentials | `aegis.identities`, `identity_roles`, `credentials` | Decide who may do what |
| Tasks, decisions and history | `aegis.tasks`, `security_decisions`, `task_state_transitions`, `jobs` | The record of what was asked for, allowed and done |
| Audit trail | `aegis.audit_events` | Accountability for security-relevant actions |
| Security policy | `aegis.policy` and `aegis.authorization` code, versioned and fingerprinted | Decides every submission and execution |

## 3. Trust boundaries

| Boundary | Between | Controls |
|---|---|---|
| B1 | Network clients and the API | Bearer tokens; strict JSON validation; 64 KiB bodies; problem details that never echo input; request IDs generated by the server; loopback only |
| B2 | API and worker processes and the database (`aegis_app`) | Column-level grants (§3.4 of the plan, pinned by a test); triggers D1–D9; append-only decisions, history and audit |
| B3 | Operators and the CLI (`aegis_owner`) | Fully trusted. Every administrative action is audited, and the last admin is protected |
| B4 | Bootstrap (superuser) | Used only to create roles and databases |
| B5 | The worker and its handlers | Closed registry of `noop` and `wait`. Handlers get only `stop_requested()` and `wait()`: no database, settings or credentials. Secret variables are removed from the process environment, though `/proc/self/environ` keeps the initial copy |
| B6 | AEGIS and NVIDIA OpenShell | **Not built** (Phase 3) |

**Who holds which secret.** After startup:

- the API holds only the `aegis_app` password and the pepper;
- the worker holds only the `aegis_app` password;
- the CLI holds the `aegis_owner` password and the pepper.

The API and worker remove every secret variable from their own environment once their settings are loaded, so neither code that reads the environment nor a child process sees them. Code in the same process can still read them from `/proc/self/environ`, which keeps the initial environment, so this is not a barrier against hostile code; Phase 1 runs none, and isolating untrusted code is OpenShell's role (Phase 3).

## 4. Threats and mitigations

Tests are named `file::test`. Unit tests are under `tests/unit`, integration tests under `tests/integration`, the security suite under `tests/security` and the end-to-end test under `tests/e2e`.

| ID | Threat | Mitigation | Verified by |
|---|---|---|---|
| T1 | A forged, stolen, expired or revoked token, or a disabled identity, is used | 32-byte secrets stored only as a peppered HMAC. Every request is checked against the database, with nothing cached. Lifetimes are 30 days by default and 90 at most. Every failure gets an identical 401. Failures involving a known credential are audited as `auth.failed` | `integration/test_api.py::test_every_authentication_failure_gets_the_identical_401`, `::test_only_failures_of_known_credentials_are_audited`, `integration/test_task_api.py::test_disabled_identities_and_revoked_credentials_get_401` |
| T2 | A caller claims to own a task, or injects correlation IDs | `owner_id` and `initiator_id` in a body get 422. The owner is always the authenticated caller, enforced by a `CHECK`. Request IDs are generated by the server, and client values are ignored | `unit/test_api_tasks.py::test_ownership_cannot_be_set_in_the_body`, `integration/test_task_api.py::test_bad_keys_and_ownership_fields_are_refused_before_anything_is_saved`, `security/test_attacks.py::test_client_supplied_request_ids_are_ignored` |
| T3 | A caller reads, lists or cancels someone else's task | Per-resource authorization. A hidden task gets the same 404 as a missing one, and the denial is saved. `scope=all` needs `task:read_any` and is audited as `task.read_privileged` | `integration/test_task_api.py::test_other_users_tasks_are_hidden`, `::test_listing_everything_requires_permission_and_is_audited`, `::test_privileged_reads_of_one_task_are_audited`, `::test_who_may_cancel_someone_elses_task` |
| T4 | Privilege escalation through the API | There are no administration routes. Permissions are defined in code and default to deny. The `worker` role is limited to system identities | `unit/test_api.py::test_the_api_exposes_only_health_me_and_tasks`, `unit/test_authorization.py`, `integration/test_identity_admin.py` |
| T5 | Misuse of the `aegis_app` credentials, for example from a compromised API or worker host | Column-level grants only; triggers that hold for every role; transitions refused without a consistent decision (D1–D9). The worker decides `task.execute` itself, so a fabricated submission still fails if its initiator may not run tasks. **Not mitigated:** fabricating a consistent allow decision or audit event (N1) | `security/test_attacks.py::test_the_application_role_holds_exactly_the_planned_privileges`, `::test_a_forged_task_still_faces_the_workers_own_checks`, `integration/test_tasks.py`, `integration/test_audit.py` |
| T6 | A task runs without the approval it needs | No transition from `awaiting_approval` to `queued` exists (D9). Tasks held for approval get no job, and workers claim only `queued` tasks. An approval-required decision at claim time holds the task | `security/test_attacks.py::test_approval_cannot_be_bypassed_with_application_credentials`, `integration/test_worker.py::test_approval_required_at_claim_holds_the_task`, `integration/test_task_api.py::test_a_long_wait_is_created_awaiting_approval` |
| T7 | Something other than a registered handler is executed | A closed, read-only registry holding exactly `noop` and `wait`. A `CHECK` on the task kind. Policy denies unregistered kinds. There are no shell or tool handlers | `unit/test_jobs.py::test_the_registry_holds_exactly_the_policy_kinds`, `security/test_attacks.py::test_unregistered_kinds_cannot_be_stored`, `integration/test_task_api.py::test_a_denied_submission_creates_nothing_and_leaves_the_key_unused` |
| T8 | The worker acts with more authority than it should (confused deputy) | The worker acts only as `system:worker`, which has no credentials, and names the initiator as subject. E1–E4 and E6 are decided at every claim, and E5 is applied. E2 and cancellation are re-checked at every heartbeat. A denied task never reaches its handler | `integration/test_worker.py::test_initiator_changes_before_the_claim_fail_the_task_without_running_it`, `::test_an_executor_without_the_worker_role_fails_the_task`, `::test_a_disabled_initiator_stops_a_running_task`, `::test_a_submitted_task_runs_to_succeeded_with_a_complete_audit_chain`, `unit/test_jobs.py::test_the_worker_forgets_every_secret_before_running_handlers` |
| T9 | A task runs twice at once, or a stale worker records a result | Claims use `SKIP LOCKED` on the task. The fencing token is the pair (job, attempt). Leases use the database clock. D8 triggers refuse attempt jumps, renewals of expired leases, and history from stale attempts or expired leases | `integration/test_worker.py::test_racing_workers_claim_a_job_exactly_once`, `::test_a_stale_worker_cannot_heartbeat_complete_or_write_history`, `::test_the_attempt_number_never_goes_down_or_jumps` |
| T10 | Retried or replayed requests create duplicate tasks | `Idempotency-Key` is required. Each initiator's submissions are serialized, with a unique key per initiator as a backstop. A different body gets 409 without disclosure | `integration/test_task_api.py::test_concurrent_identical_requests_create_one_task`, `::test_a_reused_key_with_a_different_body_conflicts_without_disclosure` |
| T11 | Audit records are altered, or a change is made without one | G1–G4 (section 7) | `integration/test_audit.py`, `integration/test_task_api.py::test_a_failed_audit_write_gives_503_and_no_task`, `security/test_failure_injection.py::test_an_audit_failure_at_completion_commits_nothing_and_the_task_is_retried` |
| T12 | Secrets leak through storage, logs, responses or the environment | Peppered hashes; redacting JSON logs; headers never logged; errors without details; decision inputs never include credentials. The API and worker drop secret variables from their environment | `security/test_attacks.py::test_no_credential_or_secret_is_stored_logged_or_returned`, `integration/test_api.py::test_tokens_never_reach_the_logs`, `unit/test_api.py::test_validation_errors_do_not_echo_input` |
| T13 | Errors or status codes disclose information | Problem details with stable codes only; identical 401s and 404s; a conflict reveals nothing about the existing task | `unit/test_api.py::test_unauthenticated_requests_get_one_identical_401`, `integration/test_task_api.py::test_other_users_tasks_are_hidden` |
| T14 | Resource exhaustion | Bodies up to 64 KiB, inputs up to 16 KiB, 10 active tasks per identity, at most 100 tasks per page, `wait` capped at 300 s, at most 10 attempts. **Not mitigated:** request rate | `unit/test_api.py::test_bodies_over_64_kib_are_refused_by_declared_length`, `integration/test_task_api.py::test_the_active_task_quota_is_enforced` |
| T15 | Configuration weakens security | Policy and authorization cannot import configuration or read the environment. Decisions are identical in every environment. Configuration can only lower the attempt limit. Unknown `AEGIS_*` variables are refused | `unit/test_layering.py`, `unit/test_policy.py::test_decisions_do_not_depend_on_the_environment`, `unit/test_jobs.py::test_configuration_cannot_raise_attempts_above_the_policy` |
| T16 | Policy changes silently | A version label and a pinned SHA-256 fingerprint of the rule sources. Every decision records both and can be replayed | `unit/test_policy.py::test_the_policy_fingerprint_is_pinned`, `integration/test_policy.py::test_saved_decisions_replay_identically` |
| T17 | A failure lets something through | Fail closed (section 5) | `tests/security/test_failure_injection.py` |
| T18 | Untrusted code escapes its sandbox | **Not applicable in Phase 1:** no untrusted code runs, and OpenShell is not built (Phase 3). Handler unit tests run under a guard that refuses network connections and subprocesses | `tests/unit/conftest.py` |
| T19 | Prompt injection, or falsified evidence | **Not applicable in Phase 1:** there are no models or agents, and no evidence verification (Phases 2, 4 and 7) | — |

## 5. Failure behaviour

| Failure | Behaviour | Verified by |
|---|---|---|
| Database unavailable to the API | Every `/v1` request and `/health/ready` gets 503; nothing is served from cache | `security/test_failure_injection.py::test_with_the_database_down_the_api_serves_no_task_request` |
| Database unavailable to the worker | The worker logs and keeps polling, and claims nothing | `security/test_failure_injection.py::test_with_the_database_down_the_worker_waits_without_failing` |
| Database lost during a run | Heartbeats fail. When the lease would have ended, the worker stops the handler, discards its result and writes nothing. Recovery retries the task | `security/test_failure_injection.py::test_an_outage_during_a_run_discards_the_result_and_recovery_retries_the_task` |
| Audit write fails in the API | 503; the change, its decision and every event roll back | `integration/test_task_api.py::test_a_failed_audit_write_gives_503_and_no_task`, `::test_reads_and_cancellations_fail_closed_when_audit_fails`, `::test_a_denial_that_cannot_be_saved_gives_503` |
| Audit write fails in the worker | A claim rolls back, so the task stays queued and unrun. A completion rolls back, so the task is retried after its lease | `security/test_failure_injection.py::test_an_audit_failure_at_claim_leaves_the_task_queued_and_unrun`, `::test_an_audit_failure_at_completion_commits_nothing_and_the_task_is_retried` |
| `auth.failed` cannot be written | The request is still refused (401), and a `CRITICAL` line is logged (N5) | `integration/test_api.py::test_a_failed_audit_write_still_refuses_the_request` |
| A policy rule raises an error | Deny with `evaluation_error`, saved. The task is never created or never run | `security/test_failure_injection.py::test_an_evaluator_error_at_submission_is_a_saved_denial`, `::test_an_evaluator_error_at_execution_fails_the_task_without_running_it` |
| A worker crashes | Its lease expires. The task goes to `interrupted`, then `queued` after backoff, or `failed` once its attempts are used up | `integration/test_worker.py::test_a_killed_workers_task_is_interrupted_retried_and_succeeds`, `e2e/test_phase1_workflow.py`, `integration/test_worker.py::test_retryable_failures_are_retried_until_attempts_run_out` |

| Schema not current | The API reports not ready (503). The worker and the CLI refuse to start | `integration/test_api.py::test_readiness_fails_when_migrations_are_behind`, `security/test_failure_injection.py::test_the_worker_refuses_to_start_on_a_schema_that_is_not_current` |
| Invalid configuration | The API, worker and CLI refuse to start, and the doctor fails its `.env` check | `unit/test_jobs.py::test_the_worker_refuses_invalid_settings_before_connecting`, `unit/test_doctor.py::test_invalid_env_configuration_fails` |

## 6. Decision integrity

Every governed state change needs a `SecurityDecision` that satisfies the consistency rules. The rules are checked by `require_consistent()` and, where possible, by the database (ADR-0006, ADR-0008, ADR-0009).

| Rule | Requirement | In code | In the database |
|---|---|---|---|
| C1 | Same task and job attempt | yes | Composite foreign keys; trigger comparing attempts; D8 requires the job's current attempt |
| C2 | The action matches the transition | yes | `task_transition_rules`, checked on every history insert |
| C3 | The effect matches the target; deny or approval-required never justifies `queued` or `running` | yes | `task_transition_rules` |
| C4 | The subject is the task's initiator | yes | Composite foreign key to the task's initiator |
| C5 | The actor is the expected one; execution is by a system identity | yes | Not enforceable; tested only |
| C6 | The resource is this task and its owner | yes | `CHECK` constraints and a composite foreign key |
| C7 | Current policy version and fingerprint | yes | Not enforceable: the database does not know the current policy |
| C8 | Decided in this transaction, used once | yes | `decided_at = occurred_at`; unique `decision_id` |
| C9 | Decided at the required stage | yes | `task_transition_rules` |

| Rule | Requirement |
|---|---|
| D1 | Only legal state changes; the version rises by exactly 1 per change |
| D2 | Every state change has its history row in the same transaction |
| D3 | A decision's fields fit together |
| D4 | The decision justifies the transition |
| D5 | Fresh and single-use decisions |
| D6 | No history row without a state change |
| D7 | A task's fixed parts never change |
| D8 | The job attempt rises only by 1, at a claim; worker history carries the current attempt; leases cannot be renewed after they expire; completion needs an unexpired lease |
| D9 | No transition from `awaiting_approval` to `queued` |

These rules prove **internal consistency, not legitimacy**. Anyone holding the `aegis_app` credentials can write a consistent but fabricated allow decision. Two backstops exist: the worker's own decision at claim time (`security/test_attacks.py::test_a_forged_task_still_faces_the_workers_own_checks`), and, from Phase 5, tamper-evidence.

## 7. Audit: what is and isn't guaranteed

This section is reproduced verbatim from the approved Phase 1 plan (§4.8) and ADR-0010.

**Guaranteed:**
- **G1. Recorded together.** Each AEGIS service operation writes its change, its decision and its audit events in one transaction. If any write fails, none is kept and the caller gets 503. So a change made through an *uncompromised* AEGIS code path is never committed without its audit events.
- **G2. No changes by the application role.** `aegis_app` has no UPDATE, DELETE or TRUNCATE privilege on the audit table, and triggers reject those for any role that hasn't disabled them.
- **G3. Database time and correlation IDs** are on every event.
- **G4. Task history is complete.** By rules D2, D6 and D8, a task's state can't change without a history row, even through direct SQL as `aegis_app`. This covers the history table, not `audit_events`.

**Not guaranteed:**
- **N1. Authenticity.** `aegis_app` can insert made-up events, including events for changes that never happened.
- **N2. Completeness under direct SQL.** `aegis_app` can change the columns it's allowed to update without writing `audit_events`. G4 still captures task state changes.
- **N3. Owner and superuser access.** Either can disable triggers and rewrite or delete anything, undetectably.
- **N4. Tamper-evidence.** There's no hash chain, signature or external anchor, and gaps in the ID sequence (which rollbacks cause) prove nothing.
- **N5. Separately written events.** Authentication failures and denials are written in their own transactions. If that write fails, the request is still denied and a high-severity log line is written instead.
- **N6. Ordinary reads** are not audited.

**Trust boundary:** audit records can be trusted only while the API and worker processes, the `aegis_app` credentials and the owner or superuser credentials are uncompromised. Phase 1 protects the audit trail from accidental change and from a buggy application, not from a compromised application or database administrator. **The hash chain, external anchoring, separating who may write audit records, and verification tools are deferred to Phase 5.**

## 8. Residual risks

- **Database credentials:**
  - `aegis_app` can fabricate consistent decisions, history and audit events (N1, N2).
  - The owner and the superuser can change anything without trace (N3).
  - There is no tamper-evidence until Phase 5 (N4).
- **No TLS and no rate limiting:**
  - The API listens only on loopback.
  - Exposing it needs a TLS-terminating proxy and a deliberate change.
- **Timing differences:** 401s and 404s are identical in content but not in timing. Known credentials and hidden tasks cost an extra write.
- **Time-of-check gaps:**
  - Authentication and the operation run in separate transactions, so a revocation takes effect at the next request.
  - Role changes and revocations during a run are not re-checked.
  - Phase 1 handlers have no side effects and run for at most 300 seconds.
- **At-least-once delivery:** a task may run again after a crash. Future handlers with outside effects need their own idempotency (Phase 4).
- **Secrets at rest:**
  - `.env` holds every secret on the developer's disk (mode 600).
  - `make` passes the file to each process, which drops the variables at startup. The initial copy stays readable in `/proc/self/environ` for the life of the process.
  - Pepper rotation is not supported.
- **No process isolation:** the API and worker run as host processes, not in containers (planned) and not under OpenShell (Phase 3).

## 9. Running the security tests

```bash
make up
make migrate
make test-security      # tests/security: attacks with stolen database credentials, secret sweep, failure injection
make test-integration   # tests/integration and tests/e2e, including the per-increment security tests
```

CI runs both on every pull request, in the required `integration-tests` job.
